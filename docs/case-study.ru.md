# Кейс: локальный privacy-airlock для ИИ-ассистента

## Проблема

Личному ИИ-ассистенту полезно качество облачной модели, но его инструкции и документы могут содержать имена, контакты, идентификаторы, адреса и ключи. Прямой запрос создаёт лишний канал раскрытия. Одной локальной LLM недостаточно: она может пропустить сущность, вернуть битый JSON или подчиниться инструкции внутри документа.

## Малое проверяемое решение

PII Airlock ставит локальную границу перед облаком. LM Studio предлагает точные чувствительные подстроки. Детерминированный код проверяет и заменяет их, второй rule-gate смотрит фактические исходящие поля, а режим по умолчанию останавливается на видимом dry-run. Если облако включено, обратно допускаются только токены той же операции.

## Собранные артефакты

- работающие Web UI, CLI и локальный API;
- 30 синтетических документов: 15 русских и 15 английских;
- offline-тесты span/overlap, TTL, форматов, остаточных секретов, поддельных токенов и stub round-trip;
- живое сравнение двух моделей LM Studio с временем каждого кейса и JSON-результатами;
- выключенный feature flag адаптера для Гоши.

## Честный результат

Запуск не доказал универсальную анонимизацию. Обе модели пропускали часть семантических сущностей; Qwen дополнительно получал schema/exact-substring ошибки на русских кейсах. Поэтому dataset-only release oracle блокировал небезопасные документы. Среди разрешённых payload было ноль известных контрольных значений, но это утверждение относится только к опубликованным fixtures и запуску. Gemma была быстрее и без schema-ошибок, однако из-за пропусков тоже остаётся экспериментальной.

## Решение по продукту

Оставить облако выключенным по умолчанию, сохранить ручной просмотр payload, дать переключатель обеих моделей и использовать gateway как fail-closed адаптер, а не как обещание. Следующий полезный эксперимент — расширить adversarial fixtures и улучшить semantic detection, не ослабляя exact-substring validation.
